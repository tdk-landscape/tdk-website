SDD is not a silver bullet. That is why TDK matters.

Practical notes for local development

SDD clarifies intent. TDK makes the system run, stay documented, and stay useful on ordinary laptops.

September 11, 2026 6 min read Article 01

Spec-driven development helps. Execution still decides whether teams move.

A good spec reduces fog. It does not boot your services, wire secrets, catch stale docs, or prove the stack works on a developer laptop.

What SDD gets right

Spec-driven development gives teams a stronger starting point. It asks people to describe intent before implementation, which makes the work easier to review and easier to hand to an AI assistant. It also gives founders and technical leads a shared artifact that is more concrete than a meeting note.

That matters. Ambiguity is expensive. A spec can name the desired behavior, the boundaries of a service, and the tradeoffs a team believes it is making. For product engineers, that is better than guessing from a ticket title. For platform engineers, it can make infrastructure expectations visible before code exists.

Where SDD stops helping

SDD does not replace product judgment. It cannot tell you whether the customer problem is worth solving, whether the architecture is overbuilt, or whether a dependency will behave under real usage. A clear spec can still describe the wrong thing with perfect confidence.

It also does not solve integration. The hard part of local microservice development is rarely writing one service in isolation. The hard part is getting databases, queues, frontends, gateways, credentials, generated clients, test runners, and documentation to agree with each other while the system keeps changing.

That is where many teams feel the gap: the spec says what should exist, but the laptop still says no.

TDK starts from one service definition, then generates the local development surface around it: Docker, TypeScript, Tilt, Starlark, docs, credentials, and assistant context.

The gap TDK fills

TDK is the execution layer below the idea. It turns service definitions into runnable local systems, then keeps generated files and generated docs aligned with the live topology. The goal is not to hide engineering reality. The goal is to make the repeatable parts boring enough that teams can focus on the judgment calls.

Each service definition can produce about {{ site.data.tdk.files_per_service }} files per service and {{ site.data.tdk.stack_artifacts }} stack-wide artifacts. Those artifacts use ordinary Docker, TypeScript, Tilt, and Starlark conventions, so teams keep the generated files and avoid lock-in.

For AI-assisted work, that structure is useful context. A generated briefing can tell an assistant what the services are, how they depend on each other, which files are generated, and where changes belong. The result is less guessing and fewer confident edits in the wrong place.

What good looks like in practice

A new engineer should be able to clone the repo, run one command, and see the whole system. Not a mock. Not one happy-path service. The databases, queues, frontends, workers, and APIs should run together on a normal machine.

TDK is built for that shape of work. That is not a replacement for production feedback. It is a practical way to make local feedback fast enough that developers keep using it.

Good local tooling should also handle the awkward parts without pretending they are elegant. Managed credentials, reproducible local stacks, generated diagrams, generated assistant briefings, and selective startup all exist because real teams have to integrate messy systems without spending every morning in Kubernetes configuration.

The honest takeaway

SDD is valuable when it improves the conversation before code. TDK is valuable when that conversation needs to become a working system. One clarifies intent. The other makes the intent runnable, inspectable, and teachable to the next developer or AI assistant.

The right promise is modest: fewer stale docs, fewer laptop setup rituals, fewer hidden credentials, and less local infrastructure ceremony. That is enough. Teams do not need a silver bullet. They need the workbench to be ready when the work begins.
